    \section{Program Overview}\label{sec:program-overview}
    The program serial implementation is divided into four main parts:

    \subsection{ReadInput}\label{subsec:readinput}
    A for loop is used to read each line of the instance file and get the number of iterations, users, items, latent features, non zero elements and the value of the convergence coefficient.
    After this step, the matrix A and a vector of the indexes of the non zero elements are then populated.

    \subsection{InitialLR}\label{subsec:initiallr}
    The routine provided was used to initialise the matrices L and R.

    \subsection{UpdateLR}\label{subsec:updatelr}
    A recommendation score is predicted for each one of the non zero elements of matrix A, using its i and j indexes to compute the internal product of the row i of the matrix L and the column j of matrix R\@.
    Afterwards, the differential between the real value of the non zero element in matrix A and its prediction is computed for all the non zero elements.
    Finally and also for each one of the non zero elements of matrix A, the selected column of matrix L and a row of R are updated to decrease the obtained differential as a function of the existing differential, the convergence coefficient and the stored matrices L and R\@.
    The function is repeated in a loop for the number of iterations and for each iteration the program stores the values of the matrices L and R and uses them to update the matrices L and R\@.

    \subsection{FilterFinalMatrix}\label{subsec:filterfinalmatrix2}
    The matrix B is computed as the multiplication of matrices L and R. Afterwards, for each row of matrix B, the maximum value is computed without taking into account the the non zero elements.
    The location of the values are stored in a vector and streamed to the standard output.


    \section{OpenMP Version}\label{sec:openmp-version}

    \subsection{Decomposition}
    \label{subsec:decompostions}
    The factorisation is a data-parallel computation. \texttt{updateLR} divides the
    non-zero list across threads --- each computes predictions and gradient increments
    for its share --- and the final stage divides matrix $B$ by rows. \texttt{initialLR}
    is left sequential: it draws pseudo-random numbers whose order is part of the
    specification, so parallelising it would race on the generator and change the result.

    \subsection{One parallel region for the whole run}
    \label{subsec:single-region}
    Rather than open a parallel region inside every iteration --- which forks and joins a
    thread team \emph{numberOfIterations} times --- we open \emph{one} region in
    \texttt{matFact} that spans the entire iteration loop. The worksharing constructs
    inside \texttt{updateLR} are \emph{orphaned}: they bind to that enclosing region, so
    the team is created once and reused for every iteration.

    \subsection{Synchronization}
    \label{subsec:synchronization}
    Each iteration must read a consistent snapshot of $L$ and $R$. The two snapshot
    copies are independent of each other, so they carry \texttt{nowait}; the prediction
    loop keeps its implicit barrier, which orders the snapshot writes before the update
    reads them. The barrier at the end of the last worksharing loop preserves the
    sequential dependence between iterations, so no thread races ahead into the next one.


    \section{Optimisations} \label{sec:optimisations}

    Every block except \texttt{initialLR} is parallelised. The interesting work was in
    \emph{how} the gradient update is parallelised, because that block carries the only
    real data hazard.

    \subsection{Lock-free update via array reduction}\label{subsec:reduction}
    The update is the hot block. Two non-zeros that share a user write the same row of
    $L$, and two that share an item write the same column of $R$, so a naive parallel
    loop has write conflicts. Guarding each write with \texttt{atomic} would serialise
    exactly the inner loop that should run in parallel. Instead we use an array
    reduction, \texttt{reduction(+ : L[:lSize], R[:rSize])}: every thread accumulates
    into a private, zero-initialised copy of $L$ and $R$ --- the increments read only the
    snapshots \texttt{StoreL}/\texttt{StoreR}, never the live factors --- and the runtime
    sums the private copies into $L$ and $R$ at the barrier. No atomics, no lock
    contention. Replacing the atomics with the reduction was the change that moved the
    program from \emph{barely matching} serial to a real speedup.

    \subsection{Conflict-free element loops}\label{subsec:conflictfree}
    Where the output partition is naturally disjoint, no synchronisation is needed at all.
    In \texttt{computeB} each thread owns a block of rows $i$, so no two threads ever
    write the same $B[i][j]$; the loop also keeps the cache-friendly $i,k,j$ order so each
    thread streams $R$ and $B$ with unit stride. The non-zero mask and the per-user
    arg-max in \texttt{filterFinalMatrix} are partitioned by row in the same way.

    \subsection{Scheduling and output}\label{subsec:scheduling}
    The element loops use \texttt{schedule(static)} (uniform work per row); the per-user
    arg-max uses \texttt{schedule(guided)}, since rows with more items cost more. The
    single \texttt{std::cout} loop runs after the region closes, so output stays ordered
    without an \texttt{ordered} clause.

    \section{Implications for Parallel and Distributed Computing}\label{sec:pdc}

    \subsection{Persistent threads beat repeated fork/join}\label{subsec:fork}
    Hoisting the parallel region trades many team set-ups for one. With short iterations
    the fork/join cost is not negligible relative to the work, so paying it once ---
    enabled by orphaned worksharing --- removes overhead that no amount of in-loop tuning
    could. The lesson generalises: keep the parallel team alive across the outer loop and
    share work inside it.

    \subsection{Resolving write conflicts: a memory-for-contention trade}\label{subsec:trade}
    The same hazard --- many updates landing on the same $L$/$R$ entries --- admits two
    answers: atomics (serialise the conflicting writes) or a reduction (give each thread a
    private copy and combine once). The reduction costs extra memory, one copy of the
    factors per thread, but removes \emph{all} contention from the inner loop. On this
    kernel that trade is decisively worth it, and it is the same trade that reappears in
    the distributed version as a gradient \texttt{Allreduce}.

    \subsection{Bandwidth, not cores, sets the ceiling}\label{subsec:bandwidth}
    The kernel streams $L$ and $R$ far more than it computes, so it is memory-bound. The
    speedup therefore flattens once a socket's memory bandwidth saturates --- around four
    threads on our machine --- rather than at the core count. The serial $i,k,j$ cache
    order is what raises that ceiling; an algorithm that is cache-inefficient in serial
    cannot be rescued by threads.

    \subsection{Synchronise exactly as much as the dependencies require}\label{subsec:sync}
    \texttt{nowait} on the independent snapshot copies, a barrier only at the true
    snapshot-then-read dependence, and the implicit end-of-loop barrier to order the
    sequential iterations: over-synchronising wastes the threads that finish early, while
    under-synchronising is a data race. Reading the dependency structure off the serial
    code is what tells you where each barrier must --- and must not --- go.

    \subsection{Amdahl in practice}\label{subsec:amdahl}
    Sequential \texttt{initialLR} and the reduction's combine step (whose cost grows with
    the thread count) are the non-parallel fractions, so by Amdahl's law the speedup is
    sublinear and eventually plateaus --- consistent with the measurements below.
