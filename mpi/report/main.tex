    \section{Program Overview}\label{sec:program-overview}
    The program serial implementation is divided into four main parts:

    \subsection{ReadInput}\label{subsec:readinput}
    A for loop is used to read each line of the instance file and get the number of iterations, users, items, latent features, non zero elements and the value of the convergence coefficient.
    After this step, the matrix A and a vector of the indexes of the non zero elements are then populated.

    \subsection{InitialLR}\label{subsec:initiallr}
    The routine provided was used to initialise the matrices L and R.

    \subsection{UpdateLR}\label{subsec:updatelr}
    A recommendation score is predicted for each one of the non zero elements of matrix A, using its i and j indexes to compute the internal product of the row i of the matrix L and the column j of matrix R\@.
    Afterwards, the differential between the real value of the non zero element in matrix A and its prediction is computed for all the non zero elements.
    Finally and also for each one of the non zero elements of matrix A, the selected column of matrix L and a row of R are updated to decrease the obtained differential as a function of the existing differential, the convergence coefficient and the stored matrices L and R\@.
    The function is repeated in a loop for the number of iterations and for each iteration the program stores the values of the matrices L and R and uses them to update the matrices L and R\@.

    \subsection{FilterFinalMatrix}\label{subsec:filterfinalmatrix2}
    The matrix B is computed as the multiplication of matrices L and R. Afterwards, for each row of matrix B, the maximum value is computed without taking into account the the non zero elements.
    The location of the values are stored in a vector and streamed to the standard output.

    \section{MPI Version}\label{sec:mpi-version}
    The MPI version uses a \emph{replicate-all} design: every process holds full copies of
    $L$ and $R$, and the only data exchanged each iteration is the gradient.

    \subsection{Foster Methodology}
    \label{subsec:foster-methodology}

    \subsubsection{ReadInput}
    \textbf{Partitioning.} The instance is parsed once, on the root.
    \textbf{Communication.} A validity status is broadcast first (so a malformed file
    aborts every rank together rather than deadlocking), then the header and the non-zero
    arrays are broadcast to all processes.
    \textbf{Agglomeration and Mapping.} After the broadcast every process holds the same
    $A$ and non-zero lists.

    \subsubsection{InitialLR}
    \textbf{Partitioning.} None: the routine is deterministic (\texttt{srandom(1)}).
    \textbf{Communication.} None --- because the seed is fixed, every process generates
    \emph{identical} $L$ and $R$ independently, so the factors never have to be broadcast.
    \textbf{Agglomeration and Mapping.} Each process keeps a full copy of $L$ and $R$.

    \subsubsection{UpdateLR}
    \textbf{Partitioning.} The non-zero list is split into one contiguous block per
    process (Quinn's \texttt{BLOCK\_LOW}/\texttt{SIZE}); each process computes the gradient
    increments for its block only.
    \textbf{Communication.} The partial gradients $dL$ and $dR$ are summed with two
    \texttt{MPI\_Allreduce(MPI\_IN\_PLACE, \ldots, MPI\_SUM)} calls, so each process ends
    the iteration with the same global increment.
    \textbf{Agglomeration and Mapping.} Each process applies that increment to its own
    snapshot of the factors, keeping every copy identical.

    \subsubsection{FilterFinalMatrix}
    \textbf{Partitioning.} Performed on the root only.
    \textbf{Communication.} None --- $L$ and $R$ are already identical everywhere.
    \textbf{Agglomeration and Mapping.} The root forms $B = L \cdot R$, masks the known
    entries, and prints one recommendation per user.

    \subsection{Decomposition}
    \label{subsec:decompostions}
    The parallelism is a \emph{domain decomposition of the gradient sum}: each non-zero's
    residual and increment are independent, so the non-zeros are split across processes and
    their contributions summed. Because the gradient is a sum the partition is arbitrary;
    we use equal contiguous blocks.

    \subsection{Synchronization}
    \label{subsec:synchronization}
    The two \texttt{Allreduce} calls per iteration are the only synchronisation: they are
    collective, so every process blocks until the global gradient is ready before applying
    it. The snapshot \texttt{StoreL}/\texttt{StoreR} guarantees that all reads in an
    iteration use the pre-iteration factors, so the result is independent of the partition
    and matches the serial output bit-for-bit at any process count.


    \section{Optimisations} \label{sec:optimisations}

    The replicate-all design is deliberately simple, and two choices keep it both correct
    and cheap.

    \subsection{Deterministic init avoids a broadcast}\label{subsec:detinit}
    Because \texttt{initialLR} is seeded with a fixed value, every process can generate the
    \emph{same} $L$ and $R$ on its own. The factors --- the largest arrays in the program
    --- therefore never travel across the network; only the per-iteration gradient does.
    A sequential property of the serial code (a fixed RNG seed) becomes a communication
    saving in the parallel one.

    \subsection{One \texttt{Allreduce} instead of many messages}\label{subsec:allreduce}
    Summing partial gradients with \texttt{MPI\_Allreduce} (rather than gathering to the
    root and scattering back) lets the MPI library use an efficient tree/ring collective
    and leaves the result already replicated on every process, exactly what the next
    iteration needs. \texttt{MPI\_IN\_PLACE} avoids a second buffer.

    \section{Implications for Parallel and Distributed Computing}\label{sec:pdc}

    \subsection{Replicate-all trades communication for simplicity}\label{subsec:tradeoff}
    Keeping a full copy of $L$ and $R$ on every process makes the code short and the
    decomposition trivial, but it has a price: the per-iteration \texttt{Allreduce} moves
    the \emph{whole} gradient, $O(\textit{features} \cdot (\textit{users} +
    \textit{items}))$ doubles, and that volume does \emph{not} shrink as processes are
    added. Compute per process falls as $1/P$ while communication per process stays
    constant, so at some point communication dominates.

    \subsection{The strong-scaling ceiling}\label{subsec:ceiling}
    This is the central lesson. On compute-heavy instances the design scales for a while;
    on \emph{wide} instances (a large $R$, hence a large gradient) it reaches the ceiling
    early and can even \emph{anti-scale} --- adding processes makes it slower, because the
    extra ranks add reduction traffic faster than they remove work. Replicate-all is a
    correct baseline, not a scalable one.

    \subsection{Memory does not scale either}\label{subsec:memory}
    Every process stores full $L$, $R$ and $A$, so the largest solvable problem is bounded
    by a \emph{single} node's memory, no matter how many nodes are used. A scalable design
    must distribute the factors, not just the work.

    \subsection{Towards a scalable design}\label{subsec:scalable}
    Both limits point the same way: stop replicating. Arranging the processes as a
    $P_r \times P_c$ grid and partitioning $L$ by user-rows and $R$ by item-columns makes
    each process own a slice of size $O((\textit{users} \cdot \textit{features} +
    \textit{features} \cdot \textit{items})/\sqrt{P})$, and replaces the global
    \texttt{Allreduce} with smaller reductions over row and column sub-communicators ---
    so communication \emph{and} memory fall with $P$. Within each process the gradient can
    be threaded with OpenMP (a hybrid model), turning the per-thread write conflict into
    the same array reduction used in the shared-memory version. The replicate-all program
    is the correctness oracle these refinements are validated against.

    \subsection{A serial tail still bounds the result}\label{subsec:amdahl}
    The final $B = L \cdot R$ and arg-max run only on the root, an
    $O(\textit{users} \cdot \textit{items} \cdot \textit{features})$ sequential tail. By
    Amdahl's law it caps the achievable speedup; distributing that stage too (as the grid
    design does) is what removes the cap.
